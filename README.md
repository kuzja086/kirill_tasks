# Навык для Алисы (Yandex Cloud Functions + PostgreSQL)

Навык для умных колонок с Алисой и приложения Яндекс. Навык реализован на Python,
публикуется как функция Яндекс Облака (Cloud Functions), данные хранит в Postgres.

Навык мотивирует ребёнка выполнять домашние задачи и копить баллы на награды.
Реализован на Python, публикуется как функция Яндекс Облака (Cloud Functions),
данные хранит в Postgres.

Что умеет навык:

- озвучить список задач на сегодня с ценой в баллах;
- принять заявку «я выполнил зарядку» и перевести задачу в ожидание подтверждения;
- назвать текущий баланс баллов;
- назвать цель и сколько баллов до неё осталось;
- показать список наград и потратить баллы на выбранную.

## Как устроена мотивация

**Задачи** (`tasks`) делятся на два вида:

| Вид | Поведение |
|---|---|
| `daily` | ежедневные и обязательные: попадают в план каждого дня |
| `random` | пул, из которого каждый день случайно выбирается N задач (по умолчанию 2) |

Выборка детерминирована парой «ребёнок + дата» (`alice_skill/plan.py`):
в течение дня набор не меняется, на следующий день — другой.

**Дневной план** (`daily_assignments`) фиксирует задачи на дату и их статусы:

```
pending → awaiting_confirmation → done
        ↘            ↘
         missed        missed
```

- `pending` — задача ещё не отмечена;
- `awaiting_confirmation` — ребёнок сказал, что выполнил; ждём подтверждения взрослого;
- `done` — подтверждено, баллы начислены;
- `missed` — не выполнено, баллы списаны.

**Баллы** хранятся как журнал (`points_ledger`): баланс = `SUM(delta)`.
Начисление `+points` происходит при подтверждении задачи; штраф `-points` —
когда день закончился, а задача осталась `pending`. Штрафы начисляются лениво:
при первом обращении к навыку в новый день (`APPLY_MISSED_PENALTIES`), поэтому
отдельный планировщик не нужен. Задачи в статусе `awaiting_confirmation`
не штрафуются: их судьбу решает подтверждение.

**Подтверждение выполнения** пока не подключено к Алисе — это отдельный
механизм (родительский чат/приложение). Точка расширения уже есть:
`PostgresSkillRepository.confirm_assignment(id)` начисляет баллы,
`.reject_assignment(id)` переводит задачу в `missed` и списывает их.

**Награды** (`rewards`) — пополняемый список: `INSERT INTO rewards (title, cost)`.
Ребёнок говорит «хочу мороженое» → создаётся заявка (`reward_redemptions`,
статус `requested`), баллы списываются сразу. Если баллов не хватает —
награда становится целью (`user_goals`), а навык говорит, сколько осталось.

### Экономика: награда раз в две недели

`alice_skill/economy.py` считает стоимость «награды за две недели» от плановых
баллов дня:

```
стоимость ≈ баллы_за_день × доля_выполнения × дни
```

Для сидов из `sql/002_seed.sql`: ежедневные задачи дают 60 баллов, две случайные
из пула — в среднем 27, итого ≈ 87 в день. При выполнении 80% за 14 дней:
`87 × 0.8 × 14 ≈ 974` → главный приз «Настольная игра» стоит **970 баллов**.
Остальные награды масштабированы относительно этого: 200 / 350 / 500 / 970 /
1100 / 2500. Изменили набор задач — пересчитайте стоимости
(`recommended_reward_cost`) и поправьте `sql/002_seed.sql`.

Сколько случайных задач выдавать в день — константа `RANDOM_TASKS_PER_DAY`
в `alice_skill/economy.py`.

### Интенты навыка

Имена должны совпадать с интентами, натренированными в консоли Яндекс.Диалогов.

| Интент | Примеры фраз | Что отвечает |
|---|---|---|
| `list_tasks` | «какие задачи на сегодня» | список задач со статусами и ценой, сумма за день, баланс |
| `my_points` | «сколько у меня баллов» | баланс и остаток до цели |
| `my_goal` | «какая у меня цель» | цель, её стоимость и сколько не хватает |
| `list_rewards` | «какие награды» | награды с ценами и пометкой «можно брать» |
| `task_done` | «я выполнил зарядку» | задача уходит в ожидание подтверждения |
| `want_reward` | «хочу мороженое» | списание баллов или установка цели |

Задачи и награды сопоставляются с фразой мягко (`alice_skill/matching.py`):
нормализация, отсечение служебных слов и грубый стемминг, поэтому
«выполнил зарядку» находит «Зарядка».

**Интенты не обязательны для запуска.** Пока модель в консоли не натренирована,
`request.nlu.intents` приходит пустым. Поэтому `dialogue.detect_intent()`
определяет интент в таком порядке:

1. `request.nlu.intents` — результат натренированной модели;
2. `request.payload.intent` — кнопки, которые навык сам отдал в ответе
   (`request.type = ButtonPressed`);
3. ключевые слова фразы (`dialogue.KEYWORD_INTENTS`): «задач/делать/план»,
   «балл/баланс», «цель/осталось», «наград/приз», «выполн/сдела/готово»,
   «хочу/купить/получить».

После обучения интентов в консоли шаги 2–3 продолжают работать как страховка,
но приоритет у NLU.


## Структура проекта

```
handler.py              точка входа Cloud Functions: handler.handler
alice_skill/
  config.py             настройки из переменных окружения (Postgres, таймауты)
  models.py             протокол Яндекс.Диалогов + предметные модели
  dialogue.py           интенты, тексты реплик, кнопки
  repository.py         SQL-операции: план дня, баллы, награды, цели
  db.py                 соединение с Postgres и транзакции
  plan.py               детерминированная выборка случайных задач
  economy.py            стоимость наград и баллы дня
  matching.py           сопоставление фразы с задачей/наградой
  text.py               склонения и строки списков
sql/001_init.sql        схема БД (применяется вручную)
sql/002_seed.sql        стартовые задачи и награды
tools/local.py          песочница: диалог и подтверждение задач без Алисы
tests/                  pytest, внешний Postgres не требуется
deploy.ps1              сборка zip и создание версии функции через yc CLI
.env.example            шаблон переменных окружения функции
```

## Требования

- Python 3.11+ (в облаке используется runtime `python312`).
- Postgres, развёрнутый локально и доступный из интернета (см. «Безопасность»).
- `yc` CLI и авторизованный профиль — только для деплоя.

## Локальная разработка

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt
pytest
```

Тесты не подключаются к базе: сценарии проверяются на in-memory реализации
`SkillRepository` (`tests/factories.py`), SQL-слой — на fake-базе со сценарием
ответов (`tests/test_repository.py`).

Применить схему и стартовые данные:

```powershell
psql -h <хост> -p 5432 -U alice_skill -d alice_skill -f sql/001_init.sql
psql -h <хост> -p 5432 -U alice_skill -d alice_skill -f sql/002_seed.sql
```

Добавить задачу или награду можно обычным `INSERT` (см. `sql/002_seed.sql`);
`is_active = false` убирает запись из плана и списка наград, не ломая историю.

### Песочница: диалог и подтверждение задач

`tools/local.py` проигрывает настоящий сценарий навыка против локальной БД
(переменные берёт из `.env`), без Алисы и облака:

```powershell
python tools/local.py today                      # план на сегодня и баланс
python tools/local.py ask "я выполнил зарядку"   # фраза ребёнка -> заявка
python tools/local.py pending                    # что ждёт подтверждения
python tools/local.py confirm 28                 # родитель подтвердил -> баллы
python tools/local.py reject 29                  # родитель отклонил -> штраф
python tools/local.py ask "какие награды"        # список наград с прогрессом
```

`--user` задаёт ребёнка (по умолчанию `local-user`), `--date` фиксирует дату
плана. Песочница же временно заменяет механизм подтверждения: в облаке он
появится отдельно, а API (`confirm_assignment` / `reject_assignment`) уже готово.


Проверить обработчик локально (нужны переменные окружения Postgres):

```powershell
$env:PG_HOST='...'; $env:PG_DATABASE='alice_skill'
$env:PG_USER='...'; $env:PG_PASSWORD='...'; $env:PG_SSLMODE='require'
python -c "import json, handler; r = handler.handler({'session': {'new': True, 'user': {'user_id': 'test'}}, 'request': {'command': ''}, 'version': '1.0'}, None); print(json.dumps(json.loads(r['body']), ensure_ascii=False, indent=2))"
```

Проверить развёрнутую функцию по HTTPS:

```powershell
$body = '{"version":"1.0","session":{"new":true,"user":{"user_id":"smoke"}},"request":{"command":""}}'
Invoke-RestMethod -Uri 'https://functions.yandexcloud.net/<id-функции>' -Method Post `
    -ContentType 'application/json; charset=utf-8' `
    -Body ([Text.Encoding]::UTF8.GetBytes($body))
```

`curl.exe -d '{"...":"..."}'` в PowerShell искажает двойные кавычки и функция
получает невалидный JSON — используйте `Invoke-RestMethod` или
`curl.exe --data-binary '@файл.json'`.

### Формат события и ответа

Функция поддерживает три режима вызова, различая их по наличию `httpMethod`
в событии (`handler._is_http_event`):

| Режим | Событие | Ответ |
|---|---|---|
| HTTPS без параметров | HTTP-событие, JSON навыка в `event['body']` | `{statusCode, headers, body, isBase64Encoded}` — платформа подставляет `body` в тело HTTP-ответа |
| HTTPS с `?integration=raw` | тело запроса как есть (строка с JSON) | чистый JSON протокола Алисы |
| `yc serverless function invoke` | сам JSON Диалогов | чистый JSON протокола Алисы |

**Для вебхука в консоли Яндекс.Диалогов используйте URL с `?integration=raw`:**

```
https://functions.yandexcloud.net/<id-функции>?integration=raw
```

Причина: консоль проверяет именно возвращаемое значение функции. Без
`integration=raw` она видит HTTP-обёртку и отвечает ошибками
«Отсутствует интент: response», «Отсутствует интент: start_account_linking»,
«Недопустимое значение поля: version». С `integration=raw` функция получает
запрос навыка напрямую и возвращает протокол без обёртки.

Обычный URL (без параметра) тоже работает для живого навыка — там платформа
сама разворачивает обёртку, — но проверка в консоли на нём спотыкается.


## Переменные окружения

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `PG_HOST` | да | — | Хост или IP локального Postgres, опубликованный в интернет |
| `PG_PORT` | нет | `5432` | Порт Postgres |
| `PG_DATABASE` | да | — | Имя базы |
| `PG_USER` | да | — | Пользователь базы |
| `PG_PASSWORD` | да | — | Пароль пользователя; храните в Lockbox (см. ниже) |
| `PG_SSLMODE` | нет | `prefer` | Режим TLS; для внешнего доступа используйте `require` |
| `PG_CONNECT_TIMEOUT` | нет | `5` | Таймаут соединения, секунды (меньше таймаута функции) |

Значения задаются в переменных окружения версии функции; локально — в `.env`,
который не коммитится.

```powershell
# Официальный установщик: кладёт yc.exe в %USERPROFILE%\yandex-cloud\bin и добавляет каталог в PATH.
# После установки откройте новый терминал, чтобы обновился PATH.
iex (New-Object System.Net.WebClient).DownloadString("https://storage.yandexcloud.net/yandexcloud-yc/install.ps1")
```

Вариант без мастера — по готовому OAuth-токену
(как получить: https://yandex.cloud/ru/docs/cli/operations/authentication/user):

```powershell
yc config profile create default

yc config set cloud-id <cloud-id>
yc config set folder-id <folder-id>

```

### Создание функции и версии

```powershell
# 1. Создать функцию (один раз)
yc serverless function create --name alice-skill

# 2. Собрать архив и создать версию функции
./deploy.ps1 -FunctionId <id-функции>

# 3. Разрешить вызов без IAM-токена (Алиса обращается к HTTPS-эндпоинту анонимно)
yc serverless function allow-unauthenticated-invoke alice-skill
```

URL функции указывается в консоли Яндекс.Диалогов в поле «Webhook URL» —
обязательно с `?integration=raw` (см. «Формат события и ответа»):

```
https://functions.yandexcloud.net/<id-функции>?integration=raw
```

Проверить только сборку архива: `./deploy.ps1 -FunctionId any -BuildOnly`.

`deploy.ps1` сохранён в UTF-8 с BOM: Windows PowerShell 5.1 иначе читает кириллицу
как ANSI и завершается ошибкой разбора (правило зафиксировано в `.editorconfig`).

### Секреты Yandex Lockbox

Пароль Postgres не должен лежать в `.env` и в открытых переменных версии.
В Lockbox он хранится зашифрованным, а Cloud Functions подставляет его в
переменную окружения при каждом вызове — код навыка при этом не меняется,
он по-прежнему читает `os.environ`.

```powershell
# 1. Сервисный аккаунт функции: именно ему нужны права на секрет.
yc iam service-account create --name alice-skill-sa

# 2. Секрет. Payload передаём через stdin: PowerShell 5.1 вырезает двойные
#    кавычки из аргументов, и JSON-строка в --payload ломается.
'[{"key":"PG_PASSWORD","text_value":"<пароль>"}]' | yc lockbox secret create --name alice-skill-pg --payload -

# 3. Разрешить сервисному аккаунту читать payload секрета.
yc lockbox secret add-access-binding --id <secret-id> `
    --role lockbox.payloadViewer --service-account-id <sa-id>

# 4. Деплой: PG_PASSWORD берётся из секрета, остальные переменные — из .env.
./deploy.ps1 -FunctionId <id-функции> `
    -SecretId <secret-id> -ServiceAccountId <sa-id> -SecretKeys PG_PASSWORD
```

Что делает скрипт: исключает перечисленные ключи из `--environment` (чтобы не
дублировать имя) и добавляет `--secret id=<secret-id>,key=PG_PASSWORD,environment-variable=PG_PASSWORD`.
Проверить результат:

```powershell
yc serverless function version get --id <version-id>
# environment: PG_HOST, PG_PORT, PG_DATABASE, PG_USER, PG_SSLMODE, PG_CONNECT_TIMEOUT
# secrets:     key: PG_PASSWORD -> environment_variable: PG_PASSWORD
```

Ротация пароля — это новая версия секрета, передеплой функции не требуется:
платформа подставляет текущую версию при каждом вызове.

```powershell
'[{"key":"PG_PASSWORD","text_value":"<новый пароль>"}]' | yc lockbox secret add-version --id <secret-id> --payload -
```

Ограничения текущей реализации `deploy.ps1`: поддерживается один секрет на
версию, имена ключей в секрете совпадают с именами переменных окружения.
Несколько секретов (например, отдельно пароль и логин) добавляются вызовом
`--secret` с разными `id` — для этого скрипт нужно расширить.

Важно: секрет, выданный через `--secret`, попадает в `os.environ` контейнера,
поэтому `DEBUG_ERRORS` и логи по-прежнему не должны печатать значения переменных.


## Как добавить сценарий

1. Завести константу интента в `alice_skill/dialogue.py` (например `INTENT_HELP`)
   и, если сценарию нужны баллы или план дня, добавить её в
   `INTENTS_WITH_DAILY_PLAN`.
2. Добавить ветку в `respond()` и функцию-обработчик, возвращающую `AliceResponse`.
3. Натренировать интент с таким именем в консоли Яндекс.Диалогов — имя интента
   из `request.nlu.intents` должно совпадать с константой.
4. Покрыть сценарий тестом в `tests/test_dialogue.py` на `FakeSkillRepository`.

Слой данных расширяется методами протокола `SkillRepository`
(`alice_skill/repository.py`) и их реализацией в `PostgresSkillRepository`.
SQL всегда параметризован (`%s`), идентификатор ребёнка — анонимный
`session.user.user_id`. Изменения баланса пишутся только в `points_ledger`,
а планировщик не нужен: план дня и штрафы создаются лениво при первом запросе.

Если меняете правила начисления или списания — обновите `sql/001_init.sql`
и `docs`-раздел «Как устроена мотивация», чтобы схема и код не разошлись.

## Безопасность

- Postgres открыт в интернет: включайте TLS (`PG_SSLMODE=require`), не используйте
  суперпользователя в `PG_USER`, ограничьте `listen_addresses`/`pg_hba.conf`
  и по возможности доступ по IP.
- Пароль хранится в Yandex Lockbox и подставляется в переменные окружения версии
  через `--secret` (см. «Секреты Yandex Lockbox»); сервисному аккаунту функции
  выдавайте только роль `lockbox.payloadViewer` на конкретный секрет.
- `.env`, ключи и архивы сборки в `.gitignore` — не коммитьте секреты.

## Ошибки и логи

Любое исключение в обработчике перехватывается: пользователь получает валидный
ответ протокола, а трейсбек попадает в логи функции
(`yc serverless function logs <name>`). Соединение с Postgres переиспользуется
между «тёплыми» вызовами и один раз переоткрывается при обрыве.

Ошибки инфраструктуры отделены от ошибок кода (`handler._error_text`):

| Что случилось | Текст для ребёнка |
|---|---|
| `OperationalError` / `InterfaceError` / `ConfigError` | «Не получилось заглянуть в дневник задач. Попросите взрослого проверить связь с базой.» |
| любое другое исключение | «Что-то пошло не так. Попробуйте ещё раз через минуту.» |

Если логи недоступны, включите `DEBUG_ERRORS=1` в переменных окружения версии —
тогда в тексте ответа будет тип и сообщение исключения. После диагностики флаг
обязательно выключите: он раскрывает внутренние детали пользователю.
